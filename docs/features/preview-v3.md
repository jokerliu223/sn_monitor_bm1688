# feature：V3.0 调机预览（与识别同进程，双路）

> 主 [README.md](../../README.md) 只写"怎么开/怎么关"；本文件写**为什么必须内嵌、参数含义、实测数据与回退路径**。
> 相关：[../CHANGELOG.md](../CHANGELOG.md)（V3.0）、[dual-camera.md](dual-camera.md)（双路来源）。

## 作用

产测网页的「调机预览台」页面上实时看两路摄像头画面，供人工调镜头高度/焦距。
V3.0 起预览**内嵌在 `sn_monitor.py` 里**，与识别共享同一路解码 —— 调镜头时识别照常在跑，
不用像 V1/V2 那样"停预览 ↔ 起识别"来回切。

## 为什么必须内嵌

相机是**单客户端源**（README 铁律 1），第二路 RTSP 连接会把已有的那条踢掉。
所以预览**不能自己再连一次**，只能用识别进程已经解码好的帧：

```
sn_preview_embed._peek()  非阻塞取最新帧
        ↓
Bmcv 硬件编 JPEG
        ↓
MJPEG 推给网页
```

`_peek` 是**非阻塞**的：拿不到帧就跳过这一轮，绝不阻塞识别主循环。

## 启停

预览**没有独立服务**了，跟着识别服务一起启停：

```bash
sudo systemctl restart sn-monitor-big     # 起识别 = 同时起了预览
sudo systemctl stop    sn-monitor-big     # 停识别 = 同时停预览
```

板子上 `:8090` 起来后，日志里会打印一行：

```
  📺 预览已启动: http://<板子IP>:8090  (front+back, 4k, 8.0fps 上限)
     识别与预览共享同一路解码，相机源仍只有 1 条 RTSP 连接
```

## 相关参数（`sn_monitor.py` 命令行）

| 参数 | 默认 | 说明 |
|---|---|---|
| `--no-preview` | 关（即默认开预览） | **一键回退到 V2 行为**：完全不启预览，识别逻辑逐字节等同 |
| `--preview-port` | `8090` | Flask 端口 |
| `--preview-fps` | `8.0` | 编码**上限**（不是保证值）。识别不受此值影响 |
| `--preview-res` | `4k` | `4k`/`1080p`/`720p`/`360p`，`4k`=不缩放。网页上也能实时切 |
| `--preview-cam` | `both` | `both`/`front`/`back`，只预览哪几路 |
| `--preview-jpeg-quality` | `80` | **仅记录**，当前 Bmcv 编码质量不可调，改这个值不生效 |

## 实测数据（2026-09-16，双路同时 4K）

| 指标 | 数值 |
|---|---|
| 单路 4K 编码 | 94 ms/帧 |
| **双路同时 4K** | **~175 ms/帧**（两路各一个线程，互不排队） |
| 双路帧率达成 | 8 fps 上限跑满，`skipped` 少量 |
| 进程 CPU | ~380%（≈4 核），系统剩 ~37% idle |
| 相机连接数 | 正/背各 **1** 条（REQ-103 达成） |

> **画面卡顿时先降分辨率**：网页工具栏切 `1080p`，编码耗时和码率都显著下降，
> 而**识别用的图完全不受影响**（识别走原始 4K 帧，与预览分辨率无关）。
>
> 关于"预览不实时"的成因（1080p 约 1s / 4K 约 1.5~2s 的链路固有延迟）与档位取舍，
> 见工作区记忆 `preview-not-realtime-latency`，此处不重复。

## 端口与"为什么网页不直连板子"

**`:8090` 在板子上，`:8099` 在 `.57` 上，不是同一个服务。** 完整链路：

```
【板子 10.80.40.53】                        【.57 10.80.40.57】        【浏览器】
FrameReader1/2 ─ 已解码帧
   └► _peek(非阻塞) ─► Bmcv 编 JPEG
       └► MJPEG :8090 ──同源中继──► :8099 ───────────────────────► 网页
          (板子上)      /api/v1/camera/*  (产测后端 FastAPI)       <img src=...>
```

- **`:8090`** = 板子上的预览服务。V3.0 起**内嵌在 `sn_monitor.py` 进程里**，随识别服务启停，没有独立单元。
- **`:8099`** = `.57` 上的产测系统后端（FastAPI/uvicorn），它自己也是「SN 抓拍」页和其它接口的服务。
- **浏览器只跟 `.57:8099` 说话**（同源），不直连板子。`.57` 的 `backend/api/camera.py` 里有一组 `/api/v1/camera/*` 接口做中继转发，板子地址写死为 `BOARD_BASE = http://10.80.40.53:8090`（可用环境变量 `PREVIEW_BOARD_BASE` 覆盖）。

**为什么要绕这一跳**：浏览器直连板子 `:8090` 需要额外开跨域，而且板子网段对办公网不直接暴露 —— 每换一台调机电脑都要改一次配置，不通用。中继后换电脑零配置。代价是本机 HTTP 一跳 <1ms，相对板子上 4K 硬件编码的 ~55ms 可忽略。

**排障含义**：网页黑屏时先分清是哪一段断了 ——
① `curl http://10.80.40.53:8090/status` 看板子预览在不在（不通 → 板子侧问题，查 `--no-preview` / Flask / 服务是否在跑）；
② `curl http://10.80.40.57:8099/api/v1/camera/status` 看 `.57` 中继通不通（① 通 ② 不通 → `.57` 后端或网络问题）。
板子侧路由为 `/stream` `/snapshot` `/status` `/resolution` `/latest_capture` `/latest_capture/image` `/health`；
`.57` 中继把它们包成 `/api/v1/camera/*` 并加 `cam` / `res` 查询参数。
`.57` 侧板子不可达时返回 **503** 并带提示（不会把 500 抛给浏览器），超时返回 504。

> `.57` 端的实现细节（含 BUG-001 的 anyio 连接泄漏修复）见该仓库自己的 `README.md`，不在本仓库维护。

## 抓拍回显（只读，不入库）

页面底部的横条会显示板子上**最近一张已配对**的抓拍图 + SN，可点击放大。
它读的是 `sn_results/` 里 `sn_<SN>_<ts>.jpg`（**要求同名 `.json` 已存在**，避免读到写一半的图），
按 mtime 取最新，**只读不写数据库**。

因此：回显看到的是"板子刚存下的"，而产测页「SN 抓拍」看到的是"uploader 上传后的"，
两者差约 5 秒（uploader 的 watch 周期），偶有不同步属正常。
回显**不会**往 `sn_captures` 表写入任何行。

## 回退路径

预览整块是**纯加法**。出问题按以下顺序退：

1. 网页上切低分辨率（最轻，`1080p` 通常就够）
2. 重启服务时加 `--no-preview`（行为等同 V2，识别不受任何影响）
3. 彻底移除：删除 `sn_preview_embed.py`，并撤掉 `sn_monitor.py` 里 4 处预览相关小改动
   （import 兜底、6 个 CLI 参数、`attach()` 调用、`finally` 里的 `preview_stop()`）

预览线程**吞掉所有异常**（README 铁律 2），且 `attach()` 外层还有 try/except ——
预览起不来只会打一行警告，识别照常。

> Flask 在 `sn_preview_embed.py` 里是**懒导入**：模块的纯逻辑（抓拍图挑选 / 档位表）在没有 Flask 的环境也能 import 和单测；
> 缺 Flask 时只打印「预览不可用」，`sn_monitor.py` 的 import 兜底会接住，识别照常跑。

## V1/V2 的独立预览服务

`preview_service.py` 是旧的独立预览服务，**已停用（`stop` + `disable`）但保留未删**，
脚本和它的接口说明见**同目录 `preview_service_README.md`**。

**为什么不删**：它读的是本地文件/独立拉流，本进程不能做的情况下（比如只想看画面、完全不希望动识别进程）
仍有参考价值；且它的 MJPEG 端点契约（`/preview/<cam>`、`/snapshot` 等）与 V3 内嵌版一致，
保留着便于对照。`deploy/` 里**故意不放** `sn-preview.service` —— 不放单元就没人会误启用它。

**为什么不启用**：它与 `sn-monitor.service` 有 `Conflicts=`，且**多占一条 RTSP 连接会踢掉识别**（单客户端源）。
